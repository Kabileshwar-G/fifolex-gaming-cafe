2. PRODUCT VISION
======================================================================

Fifolex is an operations dashboard for a gaming cafe. Its signature interface is an interactive 3D view of the venue where staff can see and manage each gaming station. It should also provide the practical tools needed to run sessions, bookings, customer records, checkout, equipment, and cafe operations.

The product must be both:
- Visually memorable: polished 3D cafe layout, clear station states, refined gaming atmosphere.
- Operationally useful: staff can quickly answer what is free, what is booked, who is playing, when a session ends, and what needs attention.

The 3D view is a working control surface connected to the same station and session data as the rest of the app. It is not just a decorative landing page. Include a clear 2D/list fallback for smaller screens, reduced-motion preferences, or devices that cannot render 3D smoothly.

Primary users:
- Owner: configures the cafe, prices, staff access, reports, and venue layout.
- Manager: oversees daily operations, bookings, staff, stations, inventory, and reports.
- Cashier: checks in guests, starts sessions, handles checkout, and takes payments recorded by the app.
- Floor staff: views station status, assists customers, moves sessions, and reports equipment issues.
- Customer (required for completion): browses availability, books, manages memberships, and receives updates.

3. RECOMMENDED TECHNICAL DIRECTION
======================================================================

Use this as a starting recommendation, not a reason to fight the existing codebase. If the project already has a sound stack, inspect it and explain before proposing a migration.

Recommended initial stack:
- Next.js App Router with React and TypeScript.
- React Three Fiber and Three.js for the interactive 3D venue view. Use the current stable compatible versions; do not select alpha packages without a clear need.
- Tailwind CSS for responsive styling, with a small reusable design system.
- Supabase/PostgreSQL for hosted database, authentication, and realtime updates if the project owner chooses Supabase. During early UI work, support a local/mock-data mode so the app is demonstrable without external credentials.
- Zod or equivalent schema validation at input boundaries.
- Use a well-maintained form library only if forms become complex.
- Use the app's package manager consistently and pin dependency versions through its lockfile.

Keep the 3D scene isolated from business logic. The database/domain layer owns truth; the 3D map and 2D list are two presentations of the same venue/station data. Build reusable components and typed domain models. Avoid giant components, duplicated business rules, and hard-coded data inside visual components.

Potential project areas (adapt to the chosen framework conventions):
- app/ or src/app/: routes and layouts
- components/: shared interface and domain components
- features/: stations, sessions, bookings, customers, checkout, reports
- lib/: database client, auth, validation, formatting, permissions
- server/: server-only actions and integrations
- types/ or domain/: typed entities and state transitions
- public/: locally owned static assets
- docs/: product decisions, data model, setup, operations

4. DESIGN AND EXPERIENCE DIRECTION
======================================================================

Create a premium gaming-cafe control room aesthetic: dark neutral surfaces, restrained neon accents, readable typography, strong contrast, purposeful depth, and clear hierarchy. Use neon as a state accent rather than covering the whole screen in glowing effects. Prioritize legibility and fast staff workflows over visual effects.

The interface should feel like a real operations product, not a generic admin template. Use believable cafe content and synthetic demo data. Make the default experience understandable to a first-time staff member.

3D floor view requirements:
- Show a perspective/isometric venue layout with rooms/areas and recognizable station pods.
- Show PS5/console, PC, VR, and other station types as configurable data; do not assume every cafe has all types.
- Allow pan, zoom, and orbit with sensible limits; include a reset-camera control.
- Select a station to open a side panel with station name, type, status, price, equipment, current session, customer/booking, and quick actions allowed for the user's role.
- Include a visible legend and text status labels.
- Encode status using color plus text/icon/pattern; never use color alone.
- Provide loading, empty, error, and no-3D/fallback states.
- Avoid excessive animation; respect reduced-motion preferences and keep the dashboard responsive.
- On mobile, default to a compact 2D station list or simplified map and retain all essential controls.
- Ensure controls can be reached by keyboard where practical and have accessible names.

Global interface requirements:
- Responsive desktop, tablet, and phone layouts.
- Consistent spacing, typography, colors, button states, modals, toasts, and empty states.
- Confirm destructive or financially meaningful actions inside the product UI.
- Clear success/error feedback and validation messages.
- Search, filters, and sorting for long station/customer/product lists.
- Useful skeleton/loading states and graceful errors.

6. DATA AND BUSINESS RULES
======================================================================

Design a normalized data model and document it before wiring complex screens. Likely entities include:
- Cafe / venue
- Room or area
- Station / equipment
- Game / platform
- Customer
- Staff user / role / permission
- Booking
- Session
- Order / order line / product
- Payment record (provider reference only, no card data)
- Membership / credit ledger (if enabled)
- Maintenance issue
- Audit event

Add venue_id/cafe_id scoping where a future multi-cafe setup might be required, but do not overbuild a complex multi-tenant SaaS platform unless requested. Preserve a clear path to more than one cafe without making the first client setup difficult.

Define status transitions explicitly. Prevent a station from having overlapping confirmed bookings or active sessions. Use server-side transactions/constraints where needed to prevent race conditions. All timestamps must have a documented timezone policy; store timestamps consistently and display them in the cafe's configured timezone. Store money as integer minor units or an equivalent exact decimal approach, never floating-point arithmetic.

Keep a human-readable audit event for booking/session status changes, session extensions, price overrides, refunds, and station maintenance state. Do not silently rewrite financial history; use adjustments or reversals.

Use synthetic demo data only. Add a clear demo mode/banner so demo data is not mistaken for live cafe records.

8. QUALITY AND VERIFICATION EXPECTATIONS
======================================================================

For each feature, define and verify the main user flow, failure flow, role permissions, and responsive behavior. Prefer focused unit tests for pricing, booking conflict detection, and state transitions; integration tests for persistence and authorization; and browser tests for key user journeys. Use the project's existing test tools if present; introduce new tooling only when it clearly adds value.

At minimum, manually verify these demo journeys in the running browser:
1. Open dashboard and find an available station.
2. Select a station in 3D, then locate the same station in the 2D/list view.
3. Create or select a synthetic customer and start a walk-in session.
4. Extend the session and confirm the timer/price updates correctly.
5. End the session and review the checkout/receipt.
6. Create a booking and verify a conflicting booking cannot be created.
7. Mark a station for maintenance and verify it cannot be booked/started.
8. Check a narrow mobile viewport and ensure all actions remain reachable.
9. Review browser console and failed network requests.

Never report a check as passing unless it was actually performed. Clearly separate verified features, mocked features, and not-yet-built features.
